# Configuración

JARVIS valida los ajustes con `Settings`. Si no se proporciona configuración, `ai_enabled` y `remote_ai_enabled` son `false`, el proveedor seleccionado es `simulated` y la aplicación conserva el flujo determinista local sin inicializar proveedores locales o remotos ni realizar llamadas de red. No se requieren credenciales para iniciar ni para ejecutar el flujo simulado.

## Selección de proveedor

| Ajuste | Valores | Predeterminado | Efecto actual |
|---|---|---|---|
| `JARVIS_AI_ENABLED` | `true` / `false` | `false` | Si es `false`, `ai_provider` debe ser `simulated`; las solicitudes informativas devuelven indisponibilidad controlada y el flujo Echo determinista continúa disponible. Si es `true` con proveedor `simulated`, solo se habilita la respuesta informativa determinista de prueba. No inicia proveedores locales o remotos. |
| `JARVIS_AI_PROVIDER` | `simulated`, `local`, `remote` | `simulated` | `simulated` no usa un modelo. `local` requiere `JARVIS_AI_ENABLED=true` y un `LocalModelManager` inyectado; puede usarse con el adaptador Ollama opcional descrito abajo. `remote` requiere simultáneamente las tres opciones de habilitación, pero sigue bloqueado por falta de una política efectiva de privacidad y de un adaptador. No hay fallback silencioso. |
| `JARVIS_REMOTE_AI_ENABLED` | `true` / `false` | `false` | Sólo puede ser `true` junto con `JARVIS_AI_ENABLED=true` y `JARVIS_AI_PROVIDER=remote`. Es una preferencia de configuración confiable, no una aprobación de seguridad: el selector todavía bloquea el proveedor remoto. No activa un transporte de red. |
| `JARVIS_LOCAL_MAX_CONTEXT_TOKENS` | entero >= 0 | `0` | Límite global de contexto que usa `LocalModelManager`; cero deja deshabilitada la admisión local. Un contador de tokens confiable inyectado mide la entrada antes de admitirla; no hay tokenizer de producción conectado. |
| `JARVIS_LOCAL_RAM_BUDGET_MB` | entero > 0 | sin configurar | Presupuesto agregado de estimaciones para modelos cargados, reservas y nuevas cargas. Sin presupuesto el gestor deniega cargas; no representa memoria libre medida. |
| `JARVIS_LOCAL_VRAM_BUDGET_MB` | entero > 0 | sin configurar | Presupuesto agregado de estimaciones para modelos cargados, reservas y nuevas cargas. Un requisito VRAM no se admite si falta presupuesto o medición disponible. |
| `JARVIS_LOCAL_MAX_SYSTEM_LOAD` | número de 0 a 1 | sin configurar | Umbral opcional expresado como fracción normalizada (1 = carga completa); su uso requiere que la fuente de recursos entregue una medida conocida en la misma escala. No hay medidor del sistema implementado. |
| `JARVIS_LOCAL_MAX_CONCURRENT_LOADS` | entero de 1 a 16 | `1` | Máximo de cargas coordinadas simultáneamente por una instancia del gestor; las solicitudes por encima del límite se rechazan sin espera. |
| `JARVIS_LOCAL_MAX_CONCURRENT_INFERENCES` | entero de 1 a 16 | `1` | Máximo de inferencias activas coordinadas por una instancia. No limita otros procesos ni gestores independientes. |
| `JARVIS_LOCAL_UNLOAD_AFTER_INFERENCE` | `true` / `false` | `true` | Descarga el handle tras una inferencia exitosa; `false` conserva el modelo listo para reutilizar. Un modelo ocupado no se descarga. |
| `JARVIS_LOCAL_OLLAMA_BASE_URL` | URL HTTP de loopback, sin ruta, credenciales, query ni fragmento | `http://127.0.0.1:11434` | Endpoint local únicamente. No acepta servicios remotos; el transporte deshabilita proxies y redirecciones. Configurarlo no inicia ni conecta Ollama por sí solo. |
| `JARVIS_LOCAL_OLLAMA_MODEL` | nombre/tag Ollama acotado o vacío | sin configurar | Modelo instalado en el servidor Ollama local. Debe fijarlo código confiable al crear el backend; no se descarga ni se selecciona a partir de la solicitud. |
| `JARVIS_LOCAL_OLLAMA_TIMEOUT_SECONDS` | número finito > 0 y <= 600 | `60` | Timeout síncrono de cada petición HTTP al servidor local. Al vencer, el cliente no puede afirmar que la inferencia del servidor se canceló; el estado de recursos queda incierto y se conserva la reserva. |
| Acceso a servicios de Internet | No hay ajuste de entorno | Denegado | La política separada `InternetAccessPolicy` deniega todas las capacidades por defecto. La selección de `remote` es solo para IA remota y no habilita búsqueda web. No hay adaptador de búsqueda ni conexión de red implementados. |
| `JARVIS_MODE` | `simulated` | `simulated` | Cualquier otro valor se rechaza. |
| `JARVIS_LOG_LEVEL` | `NOTSET`, `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` | `INFO` | Se valida y normaliza a mayúsculas. Actualmente este ajuste no configura ni cambia ningún logger. |

Las opciones booleanas aceptan `1`, `true`, `yes`, `on` y sus formas negativas `0`, `false`, `no`, `off`, sin distinguir mayúsculas. Un valor desconocido se rechaza. También se rechazan los campos no definidos al construir `Settings` y las variables desconocidas con prefijo `JARVIS_`; las variables ajenas a ese prefijo se ignoran. La combinación remota válida exige `JARVIS_AI_ENABLED=true`, `JARVIS_AI_PROVIDER=remote` y `JARVIS_REMOTE_AI_ENABLED=true`; las combinaciones incompletas o contradictorias se rechazan durante la validación antes de construir la aplicación.

Configuración de ejemplo:

```dotenv
JARVIS_MODE=simulated
JARVIS_AI_ENABLED=false
JARVIS_AI_PROVIDER=simulated
JARVIS_REMOTE_AI_ENABLED=false
JARVIS_LOG_LEVEL=INFO
```

El gestor de ciclo de vida local implementa contratos, validación y coordinación con proveedores inyectados de recursos, conteo de tokens y backend. `OllamaLocalModelBackend` implementa el backend mediante la API HTTP local: consulta disponibilidad, genera respuestas informativas y solicita/verifica la descarga. No es un motor de inferencia incluido; requiere que Ollama y el modelo estén instalados y que el servidor lo inicie el usuario. La aplicación no crea el backend ni el gestor automáticamente. Un llamador confiable puede construir el backend desde `Settings`, registrarlo en `LocalModelManager` con estimaciones confiables de recursos, un contador compatible y un proveedor de recursos que no sea simulado, e inyectar el gestor en la aplicación cuando `ai_enabled=true` y `ai_provider=local`. El backend solo admite el identificador de gestor `ollama-local`; las tareas habilitadas son `answer_question` y `summarize_text`. `load` verifica metadatos con `/api/show`, mientras Ollama puede cargar pesos al inferir; el backend pide conservarlos durante la sesión gestionada y, según la política configurada, descargarlos con `keep_alive=0`, confirmando ausencia en `/api/ps`.

La fuente `SIMULATED` solo se admite en gestores creados explícitamente para pruebas y la composición de aplicación rechaza ese modo; ningún ajuste de usuario o IA lo activa. No hay medición de hardware incorporada ni medición fiable de RAM/VRAM del proceso Ollama. Las muestras deben tener como máximo cinco segundos; datos desconocidos o insuficientes deniegan la admisión. Los presupuestos RAM/VRAM limitan estimaciones agregadas, no reservan memoria del sistema operativo ni garantizan el consumo real; los recursos pueden cambiar tras medir. El adaptador pasa `num_ctx` como límite del servidor, pero no integra un tokenizer compatible ni demuestra que el contador inyectado corresponda al modelo. El timeout HTTP es síncrono y no es cancelación efectiva: si una petición de inferencia o descarga queda incierta, se conserva la reserva y esa instancia del backend no autoriza otra descarga; puede requerirse intervención externa. El cliente estándar usa el mismo timeout para conexión y lectura. La concurrencia solo se coordina dentro de una instancia del gestor. El adaptador remoto, la gestión de credenciales, el consentimiento explícito por solicitud y el envío a servicios externos siguen sin implementarse. La API Ollama se limita a loopback; la política separada de servicios de Internet no se habilita. No se debe enviar contenido fuera del equipo antes de definir y probar consentimiento y política para datos sensibles. La respuesta informativa está limitada a 16.000 caracteres; los parámetros de herramientas están acotados a 8.000 caracteres por cadena o clave, 32 niveles, 256 elementos por contenedor y 2.048 nodos.
