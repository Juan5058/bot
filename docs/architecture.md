# Arquitectura de JARVIS CORE

## Objetivo

Construir un núcleo local, seguro y extensible para una aplicación de asistente personal para Windows, con texto como interfaz primaria y ejecución simulada por defecto.

## Capas

- config: validación de configuración y entorno.
- core: contexto, errores e interfaces de contrato.
- conversation: entrada, intención y flujo del usuario.
- ai: proveedores de IA con un simulador determinista.
- security: política, autorización y auditoría.
- tools: definición, registro y ejecución ejecutada en modo simulado.

## Principios

- Denegación por defecto.
- IA propone, seguridad autoriza, herramientas ejecutan.
- Los proveedores son intercambiables.
- El modo simulado es la única ruta implementada.
- La seguridad se valida en el momento de usar la herramienta.
- El contexto de sesión no contiene permisos otorgados; sólo contiene contexto y trazabilidad.

## Contrato y selección del proveedor de IA

- `AIProviderSelector` consume el `RouteDecision` existente: las rutas incompletas/rechazadas son terminales, Echo requiere que `echo_message` exista en el registro confiable, y solo una ruta generativa válida puede seleccionar un proveedor. El catálogo contiene únicamente adaptadores realmente registrados; una selección local sin adaptador se informa como indisponible y no recurre al simulador.
- La selección local es una preferencia de proveedor, no un permiso de seguridad. Seleccionar un proveedor no crea propuestas ni autoriza herramientas; Echo sigue usando su flujo independiente de propuesta confiable, autorización, auditoría y runner.
- El proveedor remoto permanece bloqueado incluso si `ai_enabled`, `ai_provider="remote"` y `remote_ai_enabled` están configurados. Todavía no hay un control efectivo para evitar que datos sensibles no autorizados lleguen al adaptador; la bandera de configuración no sustituye ese control.
- `LocalModelManager` proporciona contratos de catálogo, admisión y ciclo de vida desacoplados del motor. Los descriptores declaran tareas, contexto máximo y estimaciones de RAM/VRAM; las estimaciones no son mediciones ni reservas del sistema operativo. La admisión exige una instantánea conocida y reciente (máximo cinco segundos), presupuesto configurado y disponibilidad suficiente para modelos ya cargados, reservas de carga y el nuevo modelo. La comprobación es conservadora y puede volver a contar modelos que el sistema operativo ya refleja como memoria ocupada. Un `ContextTokenCounter` confiable inyectado cuenta el contenido antes de admitirlo; no hay tokenizer de producción conectado y las pruebas usan un contador simulado. Una medición puede quedar obsoleta o los recursos externos pueden cambiar entre comprobación y carga; el backend real debe tratar el fallo de asignación de forma segura. La aplicación rechaza gestores habilitados para recursos simulados y no registra modelos por configuración ni construye un backend real: `local` queda indisponible de forma predeterminada, aunque un adaptador informativo puede componerse con un gestor inyectado y límites coincidentes.
- `OllamaLocalModelBackend` implementa el contrato de backend existente mediante la API HTTP de Ollama en loopback. Comprueba el modelo con `/api/show`, genera texto informativo no transmitido en streaming y solicita la descarga con `keep_alive=0`, verificándola mediante `/api/ps`. Su método `load` verifica disponibilidad pero no precarga pesos; Ollama los carga al inferir. El backend está disponible solo como componente inyectable: la aplicación no crea un gestor, no selecciona modelos ni se conecta a Ollama automáticamente. El modelo y el endpoint se configuran explícitamente, las redirecciones y proxies se deshabilitan, y la salida permanece texto no confiable dentro de `respond_informational`.
- `ManagedLocalAIProvider` adapta el gestor a las solicitudes informativas tipadas de `AIProviderContract`. No implementa clasificación ni propuestas de acciones; sus métodos no informativos fallan cerrados. La selección pasa por el `AIProviderSelector` existente y la respuesta informativa no alcanza autorización ni runner. La inyección de un backend y un contador confiables es una extensión de composición, no una vía para que una solicitud o salida de modelo registre capacidades o cambie límites.
- El gestor aplica límites configurados de contexto, presupuesto agregado estimado, cargas e inferencias simultáneas. Las solicitudes que exceden concurrencia se rechazan inmediatamente; no esperan ni inician cargas duplicadas del mismo modelo. El modelo se conserva listo o se descarga al finalizar según `local_unload_after_inference` (predeterminado `true`); la descarga explícita de un modelo ocupado se rechaza.
- Las configuraciones locales predeterminadas deshabilitan admisión: contexto máximo cero y ningún presupuesto RAM. No se eligen límites óptimos de hardware. `local_max_system_load` solo se puede aplicar si el proveedor de recursos entrega una medida conocida; no existe actualmente un medidor real de carga.
- El contador de tokens, el backend y el proveedor de recursos son síncronos. El gestor no implementa timeout ni cancelación efectiva y no puede interrumpir un conteo, lectura de recursos o carga/inferencia bloqueante; tampoco promete que una llamada bloqueante no detenga el hilo llamador. El timeout HTTP de Ollama limita la espera del cliente, pero no demuestra que una inferencia en el servidor haya sido cancelada. Si se pierde la certeza de una inferencia o descarga, el adaptador conserva el estado incierto y rechaza liberar el modelo; puede requerirse una intervención/reinicio externo para recuperar esa instancia. Una interrupción de Python tampoco detiene necesariamente el backend. El backend debe implementar `failed_load_released(model_id)` y confirmar explícitamente que una carga fallida liberó sus asignaciones; sin confirmación el gestor conserva la reserva y bloquea nuevos intentos. Una descarga solo libera la reserva si el backend retorna con éxito. Para garantizar plazos y cancelación hace falta aislar estas operaciones en un proceso terminable o usar contratos cancelables comprobables.
- Los servicios externos de Internet son una capacidad distinta de los proveedores de IA. `web: <consulta>` y `busca en Internet: <consulta>` se interpretan como solicitudes `WEB_SEARCH`; el selector de IA las termina sin seleccionar IA. `InternetAccessPolicy` es una política separada y deniega por defecto. El pipeline comprueba explícitamente `POLICY_DENIED` y falla de forma cerrada; en cualquier otro resultado la búsqueda también queda no disponible mientras no haya un adaptador y un contrato de ejecución integrados. Actualmente no se invoca red ni se inventan resultados. El proveedor online de IA no es requisito para esta ruta.
- `RequestEnvelope` valida texto no vacío de hasta 8.000 caracteres y genera un identificador aleatorio de solicitud. `RouteDecision` es el contrato canónico de interpretación: conserva la solicitud validada, una capacidad enumerada, parámetros estructuralmente validados, faltantes/ambigüedades enumerados, estado derivado de la categoría y procedencia controlada. Solo `DETERMINISTIC_ROUTER` está disponible; la procedencia no expresa confianza ni autoridad. El contrato no contiene permisos ni claims. `DeterministicRequestRouter` reconoce `repite: <texto>` y `echo: <texto>` para Echo; `pregunta: <texto>` y `resumen: <texto>` son candidatas únicamente a respuesta informativa. Argumentos faltantes piden aclaración. Acciones locales, búsquedas sin el prefijo explícito y texto libre no reconocido no se convierten en rutas ejecutables.
- El estado derivado expresa el resultado de interpretación, no la ejecutabilidad: una ruta generativa válida tiene estado `understood` aunque solo sea candidata a respuesta informativa; `unsupported` se reserva para rutas rechazadas, y las rutas incompletas tienen `needs_clarification`.
- El router tiene prioridad y no consulta al proveedor ni autoriza. Una ruta Echo crea una propuesta interna desde la definición confiable del registro; el runner aún valida, autoriza, audita antes del despacho y ejecuta solo el Echo simulado. Una ruta informativa, únicamente cuando `ai_enabled=true` y existe el método tipado del proveedor, llama a `respond_informational` y devuelve texto separado de `tool_result`; no construye propuestas ni alcanza el autorizador o runner. Con IA desactivada o proveedor sin ese método se devuelve indisponibilidad controlada. El proveedor simulado genera una respuesta determinista de prueba, no realiza inferencia.
- `AIProviderContract` separa clasificación/sugerencia de acciones de `respond_informational(InformationalRequest) -> InformationalResponse`. La ruta informativa no usa `ActionSuggestion`, `classify_intent`, `propose_action` ni `respond`.
- El proveedor informativo recibe únicamente la capacidad informativa enumerada y el texto posterior al prefijo; no recibe el contexto de sesión, claims, permisos, confirmaciones ni política. La respuesta se valida como texto no vacío de hasta 16.000 caracteres y no puede ser una acción.
- Cuando se integre un proveedor en una fase posterior, su sugerencia contendrá únicamente el nombre de la herramienta y sus parámetros. El pipeline deberá comprobar tipo, registro y límites, y obtener permiso, riesgo y requisitos de confirmación del catálogo confiable; una sugerencia inválida deberá rechazarse antes del runner. Ese flujo aún no forma parte del comportamiento implementado.
- Cada entrada del catálogo confiable define el esquema de argumentos de su herramienta. `echo_message` acepta exactamente un diccionario con el campo obligatorio `message`, de tipo exacto `str` y longitud de 0 a 8.000 caracteres; rechaza campos adicionales. El pipeline, el autorizador y el runner comprueban este esquema. El runner valida una copia defensiva, autoriza esa propuesta y ejecuta los mismos argumentos copiados.
- El registro expone nombres, definiciones confiables y validación, no instancias ejecutables. El constructor normal de `SimulatedToolRunner` no acepta ejecutores proporcionados por el llamador; solo compone el ejecutor Echo incorporado si el registro coincide con el catálogo confiable. La definición `EchoTool` no tiene un método público de ejecución; el controlador simulado se despacha después de validar y autorizar.
- Las pruebas que requieren ejecutores contadores usan directamente el despachador interno con un mapa de prueba separado. No se utiliza esa vía para componer la aplicación normal y no proporciona aislamiento frente a código Python arbitrario en el proceso.
- Esta separación evita el acceso accidental mediante las APIs públicas soportadas, pero no es una frontera contra código Python malicioso dentro del proceso: tal código puede inspeccionar o alterar objetos privados y módulos.
- Los parámetros se limitan a JSON compatible con profundidad máxima de 32, 256 elementos por contenedor, 2.048 nodos, y cadenas/claves de hasta 8.000 caracteres. El runner crea y revalida una copia antes de autorizarla y ejecuta esa misma propuesta copiada.
- Los parámetros de una interpretación se copian, validan y congelan recursivamente; mapas se exponen como vistas de solo lectura y listas como tuplas. El pipeline produce una copia mutable independiente solo en el límite de validación del esquema confiable, vuelve a validar esa copia y únicamente entonces construye la propuesta. La interpretación no llama al autorizador ni al runner; la política y el runner conservan sus responsabilidades independientes.
- `ConversationResult.to_dict()` publica `user_text`, `intent`, `success`, `tool_result` y `error`; solo agrega `response` para una respuesta informativa válida. Para Echo, conserva el mensaje exacto y un estado simulado. No publica propuestas, permisos, riesgo, referencias de acción, estado de autorización ni identificadores de auditoría. Los errores se restringen a mensajes conocidos; cualquier texto de error no reconocido se sustituye por un mensaje genérico. `user_text`, el mensaje Echo y la respuesta informativa pueden contener información sensible. No existe detección universal de secretos en texto arbitrario.
- Las respuestas informativas no generan eventos de auditoría en esta fase: no hay ejecución ni decisión de autorización que registrar, y se evita persistir metadatos de una consulta potencialmente sensible. Esto limita la trazabilidad de uso/errores; si una necesidad operativa futura justifica eventos, deberán limitarse a códigos y metadatos mínimos sin texto de solicitud o respuesta.
- El flujo de ejecución continúa por `AuthorizationService` y `SimulatedToolRunner`; la selección del proveedor no cambia la política.
- La política de herramientas locales y la política de acceso a Internet son independientes: `InternetAccessPolicy` no concede permisos de herramientas, y `AuthorizationService` no habilita acceso de red. Ninguna solicitud o salida del proveedor puede modificar estas políticas o el contexto de autorización.
- `simulated` es el proveedor predeterminado y el único proveedor conectado en esta etapa. `local` y `remote` se reconocen como selecciones explícitas; si no hay adaptador disponible, las solicitudes devuelven indisponibilidad controlada y no usan fallback.
- El proveedor remoto requiere seleccionar `remote` y habilitar `remote_ai_enabled`; su valor predeterminado es `false`. Incluso habilitado en configuración, no hay transporte ni inferencia remota implementados en esta etapa.
- `ai_enabled=false` mantiene el flujo simulado determinista y las solicitudes informativas devuelven indisponibilidad controlada; requiere `ai_provider="simulated"` y no inicializa proveedores locales o remotos. Con `ai_enabled=true` y `ai_provider="simulated"`, solo se activa la respuesta informativa simulada determinista. La selección local sin adaptador disponible devuelve indisponibilidad controlada.
- El proveedor remoto requiere simultáneamente `ai_enabled=true`, `ai_provider="remote"` y `remote_ai_enabled=true`. Las combinaciones contradictorias se rechazan por validación antes de crear la aplicación. Aunque se cumplan las tres opciones, el selector bloquea el uso remoto hasta que haya adaptador y controles efectivos de privacidad; nunca hay fallback ni transporte en esta etapa.
- Contrato previsto para proveedores: `propose_action(user_text)` devuelve `ActionSuggestion` (nombre y parámetros), y `respond(user_text)` no recibe `ConversationContext`. Los antiguos `ToolProposal` de proveedor no se aceptan; al integrar propuestas, el pipeline deberá construirlas a partir del catálogo confiable.

La integración local/remota real, el consentimiento explícito por solicitud, la minimización específica de datos y las políticas de privacidad por proveedor quedan pendientes. No se permite enviar contenido fuera del equipo hasta definir y probar esos controles. Antes de habilitar transporte remoto también serán obligatorios límites efectivos de tiempo y recursos, cancelación de operaciones excedidas, tamaño de respuesta, pruebas de errores y bloqueo de comunicaciones cuando el proveedor no esté explícitamente habilitado. El flujo síncrono actual no impone un timeout efectivo.

La capacidad `WEB_SEARCH` y su política denegada por defecto solo permiten expresar y rechazar la ruta: no hay adaptador, catálogo de resultados, cliente HTTP ni transporte. Un futuro adaptador deberá tener una política de red separada con destinos/protocolos permitidos, límites de solicitud/respuesta y controles de privacidad; nunca deberá requerir un proveedor de IA online.

### Contrato futuro de ejecución de proveedores (no implementado)

- Mantener `InformationalRequest` como datos de la consulta. Los límites de ejecución deben proceder de configuración confiable del host, nunca del usuario ni del proveedor. Si se incorpora un contexto tipado, debe ser un argumento separado que contenga un deadline absoluto monotónico y presupuestos explícitos de entrada/salida y recursos aplicables al backend.
- El adaptador debe imponer el deadline en la operación real y propagar cancelación al transporte o motor. Un timeout en el hilo llamador que deja una llamada bloqueante viva no es un timeout efectivo; si el backend no ofrece cancelación acotada, no se debe prometer cancelación ni disponibilidad dura hasta aislarlo en un proceso terminable.
- Los resultados recibidos después del deadline o de la cancelación se descartan y nunca se convierten en respuestas exitosas. El contrato futuro debe distinguir éxito validado de timeout, cancelación, indisponibilidad y salida inválida, sin incluir excepciones crudas en el resultado público.
- El adaptador debe liberar conexiones, handles y memoria temporal en rutas de éxito, error, timeout y cancelación. Debe probarse que la liberación ocurre también ante respuesta tardía; cerrar recursos en el hilo llamador no basta si una operación bloqueante continúa ejecutándose.
- La coordinación de concurrencia, el límite de contexto y la admisión por presupuestos estimados viven en `LocalModelManager`, no en `AIProviderContract`. Esos límites solo coordinan una instancia y dependen de requisitos declarados; no imponen límites de CPU/RAM/VRAM al proceso ni garantizan cancelación o deadline del backend.

### Gestor local (infraestructura, sin motor)

- `LocalModelDescriptor`, `ModelRequirements`, `ResourceSnapshot` y `LocalModelLimits` validan identificadores controlados, capacidades, límites, estimaciones y antigüedad de medición. `ResourceSource.SIMULATED` solo se acepta en gestores creados explícitamente para pruebas y la composición de aplicación rechaza esos gestores; ningún ajuste de usuario o IA activa el modo. Un origen desconocido, una medición de más de cinco segundos, RAM desconocida, presupuesto no configurado o VRAM desconocida necesaria deniegan la admisión.
- `LocalModelManager` serializa transiciones y reservas estimadas con un lock breve, contabiliza modelos cargados y cargas en curso contra presupuestos y disponibilidad declarada, y efectúa carga/inferencia/descarga fuera del lock. No espera por cupos; las solicitudes concurrentes no admitidas reciben indisponibilidad. Los errores públicos omiten mensajes del backend. Una carga fallida libera su reserva solo si `failed_load_released` confirma la liberación; de lo contrario conserva la reserva y bloquea reintentos. Una descarga libera la reserva únicamente tras retorno exitoso.
- Las capacidades verificables son lógica de estado, admisión estimada, límites y coordinación con backends, contadores y proveedores de recursos inyectados. No hay catálogo de modelos reales, motor, tokenizer de producción, medidor OS/VRAM, gestión de hilos/procesos, timeout o cancelación de operaciones síncronas. El contador confiable calcula `context_tokens`; el backend real deberá imponer también el límite al contexto efectivo.
